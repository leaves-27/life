# 


需求调研的核心不是“收集一堆想法”，而是降低做错方向的风险：搞清楚业务目标、用户真实问题、约束条件和优先级，最终形成可决策、可验证的需求结论。

可以按“调研前—调研中—调研后”来做。

一、调研前：先定义“为什么调研”
1. 明确调研目标
先回答：

这次调研要支持什么决策？做不做？做什么？先做哪个？

业务目标是什么？增收、降本、提效、合规、留存？

调研边界是什么？用户、场景、时间、系统范围。

输出什么？需求清单、用户画像、流程现状、优先级、商业论证？

不要一开始就问“你们想要什么功能”，先问“要解决什么问题”。

2. 识别干系人
常见对象：

业务方/老板：目标、预算、优先级、成功标准

一线用户：真实场景、痛点、工作流、替代方案

运营/销售/客服：高频问题、投诉、流失原因

技术/数据/法务/财务：约束、成本、合规、数据可得性

现有系统管理员：流程、权限、历史包袱

可用“权力—利益”矩阵区分：重点管理、重点满足、保持告知、持续观察。

3. 选择调研方法
目的	方法
了解真实场景和动机	深度访谈、现场观察、影子跟随
验证普遍性	问卷、数据分析
了解流程和异常	流程走查、工作坊
了解市场和替代方案	竞品分析、行业报告
验证方案	原型测试、可用性测试
找高频问题	客服记录、工单、埋点、搜索日志
通常组合使用：访谈找假设 → 问卷/数据验证规模 → 原型验证方案。

4. 设计访谈提纲
问题要围绕“事实和过去行为”，少问“你觉得/你希望”。
可参考：

你最近一次做这件事是什么时候？能完整讲一遍吗？

过程中最费时间/最容易出错的是哪一步？为什么？

现在用什么方式解决？哪些工具/表格/人？

如果问题没解决，会有什么后果？影响多大、多久一次？

你尝试过哪些替代方案？为什么没用？

谁还参与这个流程？谁审批、谁录入、谁查看？

如果只能改一个地方，你最希望改哪里？为什么？

什么情况下这件事必须成功？失败会怎样？

二、调研中：多听事实，少诱导
1. 访谈技巧
先寒暄说明目的，不承诺“一定做”。

让用户讲具体案例，追问“然后呢、为什么、多久一次、影响谁”。

区分：事实、观点、情绪、需求、方案。

用户说“我要一个报表”，追问“你拿报表做什么决策？现在怎么做的？”

用户说“要快”，追问“多快算快？现在多慢？慢导致什么损失？”

记录原话，不急着下结论。

2. 现场观察
很多需求在访谈中说不出来，要看真实操作：

实际步骤、临时表格、线下沟通、重复录入、异常处理。

记录频率、耗时、错误率、参与角色、系统切换。

3. 数据验证
用数据判断“是个例还是普遍问题”：

业务量、转化率、流失率、工单量、投诉类型

功能使用率、路径漏斗、搜索词、失败率

人工处理时长、返工率、差错率

4. 工作坊
适合跨部门对齐流程和优先级：

先画现状流程图

标出痛点、瓶颈、风险

再讨论目标流程

最后形成需求池和优先级

三、调研后：从信息到需求
1. 整理原始材料
把访谈记录、问卷、数据、观察记录统一编码：

用户角色

场景

痛点

当前解决方案

影响/频率

需求陈述

证据来源

2. 区分需求层次
业务需求：为什么做，业务目标是什么

用户需求：谁在什么场景下要完成什么

功能需求：系统要提供什么能力

非功能需求：性能、权限、安全、合规、可用性

3. 写清楚需求陈述
推荐格式：

作为【角色】，在【场景】下，我需要【完成目标】，以便【业务价值】。当前问题是【痛点/证据】。

避免只写“增加导出按钮”，要写清背后的决策场景。

4. 做优先级
常用维度：

业务价值/影响面

频率

紧急程度

实现成本

风险/合规

依赖关系

可用 MoSCoW：必须有、应该有、可以有、这次不做。或用价值—成本矩阵。

5. 输出调研报告
建议包含：

调研背景与目标

对象与方法

关键发现（带证据）

用户角色与核心场景

现状流程与痛点

需求清单与优先级

建议方案/范围

风险、假设、待确认问题

附录：访谈记录、问卷、数据

6. 回放验证
把结论拿给业务方和用户确认：

我们理解的问题对吗？

场景是否完整？

优先级是否认同？

哪些是假设，需要后续验证？

四、一个可直接套用的调研流程
定目标：这次要支持什么决策？

列假设：我们目前认为问题是什么？

选对象：业务方、用户、一线、技术、数据。

选方法：访谈 + 观察 + 数据 + 问卷/竞品。

做提纲：围绕场景、行为、痛点、影响、替代方案。

执行记录：原话、事实、数据、截图、流程。

分析归纳：按角色/场景/痛点/频率/影响聚类。

形成需求：业务需求→用户故事→功能/非功能需求。

排优先级：价值、频率、成本、风险。

回放确认：和干系人验证，形成结论和待办。

五、常见坑
只问“你想要什么功能”，不问背后问题。

只访谈老板，不访谈一线用户。

样本太少就下结论。

把用户说的“方案”直接当需求。

忽略非功能需求：权限、合规、性能、数据口径。

没有记录证据，后面无法判断优先级。

调研完没有结论和决策建议，只交一堆访谈记录。

不确认假设，把推测当事实。

一句话总结：需求调研 = 用多种方法获取事实与证据，区分问题与方案，形成带优先级和验证结论的需求决策材料。
